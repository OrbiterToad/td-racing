# Agent instructions

These instructions apply to every coding agent working in this repository.
They are synced from the shared
[agent-coordinator template](https://github.com/OrbiterToad/agent-coordinator-template);
do not edit this file in a consuming project. Change the template instead.

**Project-specific rules:** if the repository has an `AGENTS.project.md`
file, read it before you start and follow it as well. It names the default
branch, required checks, commands, and any project conventions. Where it is
more specific than this file, it wins.

## Task scope and coordinator-only guidance

- Work only on the assigned issue. Do not broaden scope or start a competing
  task without asking the coordinator.
- `CORDINATOR_AGENT.md` (and any `CORDINATOR_AGENT.project.md`) is for the
  coordinator only. Do not read, quote, or include it in your task prompt
  unless the coordinator explicitly assigns an instruction-maintenance task.
- Preserve user data, secrets, and assets. Do not delete assets or generated
  files unless the assigned issue clearly requires it.

## Commits, branches, and worktrees

Commit every change you make locally and push your commits to `origin`.
Commit and push regular, incremental milestones during implementation rather
than accumulating the entire task in an uncommitted working tree. Each commit
should be a coherent, reviewable increment that is not knowingly broken and
does not include secrets or generated noise; keep using the required commit
message format and run relevant checks before handoff.

Use the following commit message format:

`<type>(<scope>): <description>`

Example: `fix(input): preserve simultaneous key presses`

Branches created by AI must use the format `ai/<description>`, unless the
coordinator specifies otherwise.

Example: `ai/preserve-simultaneous-keys`

When working on a branch, use a temporary directory or Git worktree outside
the primary repository checkout. Do not switch the primary checkout to the
working branch; create and work in an isolated temporary checkout instead.

You may use an available GitHub token from the `GITHUB_TOKEN` or `GH_TOKEN`
environment variable, or the repository-root `GITHUB_TOKEN` file, for GitHub
operations needed to complete the task. Never print token values or include
them in logs, messages, or commits. Keep local token files ignored by Git.
Respect branch protection: use pull requests and merge only after all required
checks pass.

## Preflight before editing

1. Confirm the assigned issue is open and read its scope, acceptance
   criteria, and exclusions.
2. Fetch the current remote default branch and record its exact SHA. Do not
   assume the branch is named `main` or `master`; use the name from
   `AGENTS.project.md` or the remote.
3. Inspect open PRs, local and remote branches, worktrees, and uncommitted
   changes to detect duplicate assignments and understand integration risk.
4. Identify the repository's required checks from its CI workflows, branch
   protection, and `AGENTS.project.md`, plus any task-specific checks.
5. Send the preflight handoff (see below), then start implementing.

## Parallel work and integration

- Work in your own isolated branch or worktree. You may implement changes to
  files another agent is also changing on a separate branch; shared-file
  overlap alone is not a reason to stop or wait. Check existing assignments
  to avoid duplicating the same issue, and tell the coordinator about likely
  integration conflicts when you report progress.
- Do not edit another agent's branch or worktree, and do not merge or rebase
  another agent's changes. Keep your own changes scoped and commit/push
  reviewable milestones regularly.
- When your PR is ready, tell the coordinator “I want to merge PR #X” and
  provide the tested head and base SHAs, required check/review state, and any
  conflict notes. The coordinator owns merge ordering and gets conflicts
  resolved; if it delegates a conflict resolution on your branch to you,
  resolve it while preserving every side's intended change. Pause pushes only
  when asked while your branch is being integrated.
- A shared-file conflict is handled during integration; it is not a reason to
  leave an assigned task idle. Escalate actual blockers such as missing
  requirements, unavailable dependencies, or failing checks that you cannot
  resolve, and state the next useful step you can take.

## Validation and browser tests

- Run the task-relevant tests and the repository-required checks before
  handing off a PR. Re-check the exact final commit, not an earlier local
  state. Report the exact tested SHA and the status of each required check.
- When the user has allowed it (the coordinator or `AGENTS.project.md` says
  so), you may push after the fast checks (formatting, lint, unit tests,
  build) plus the browser or integration specs that target your change, and
  let CI run the full suite on the pushed head. Do not request a merge until
  every required CI check has passed on that head.
- If a check fails, determine whether it is caused by your change or is a
  pre-existing baseline failure. Report evidence; do not hide, skip, or
  silently weaken a test.
- For browser tests, use a free port supported by the project's test
  configuration. Keep and poll the same long-running command session instead
  of starting duplicate servers. Never stop a server or process owned by
  another worktree.

## Pull requests and merges

- Open or update a PR against the repository's default branch and link it to
  the assigned issue with an appropriate closing reference.
- Keep the task open while its pull request is pending. Follow up on review
  and required checks, and address failures.
- Do not merge, enable auto-merge, bypass branch protection, or change
  required checks. When the PR is ready, request merge readiness in the
  coordinator chat with the PR link, head and base SHAs, and required check
  and review state. The coordinator owns the merge queue and performs or
  delegates merges; merge only a specific PR and head the coordinator
  explicitly delegated to you.
- After an authorized merge, confirm it in the coordinator chat with the
  resulting default-branch SHA. Consider the task complete only after the
  merge and report that you are ready for a new task.

## Chat titles and parked work

Active agent chats are titled `Agent N (Mini/Big) · <state> · <short task>`,
for example `Agent 5 (Big) · Blocked · Gamepad support`. The title is updated
on every state change (for example `Working`, `Running checks`, `Blocked`,
`Merge ready`, `Waiting for merge`). If you can rename your own chat, update
it yourself whenever your state changes, keeping your agent number and size;
otherwise the coordinator does it. Never leave a blocked task titled
`Working`.

When implementation is complete but a PR remains in the merge queue, the
coordinator renames this task chat `Waiting for PR · <short task>` without an
agent number and reuses the numbered slot for a new assignment. A blocked
task may similarly become `Paused · <short task>`. Keep this chat, branch and
PR open for review, checks and follow-up until the assignment is complete; a
released slot does not mean the PR merged.

## Communication standard

Use these two-line structures for every direct coordination message:

```text
[Agent <number>] [#<issue> <short task>] [<state>]
Further info: <outcome or request; relevant evidence; next action and owner>
```

```text
[Coordinator] [#<issue> <short task>] [<state>]
Further info: <decision or instruction; relevant evidence; next action and owner>
```

Use the assigned agent number and tracked issue, with a short, stable task
name. If the coordinator releases the number and keeps the task chat open as
`Waiting for PR` or `Paused`, use the former number in that task's handoffs;
the issue field distinguishes it from a new assignment using that slot.
Choose a state from `assignment`, `preflight complete`, `progress`,
`blocked`, `merge request`, `decision`, `changes requested`, `merged`, or
`ready for new task`. Where the project publishes a coordinator guide (for
example `docs/COORDINATOR_GUIDE.md`), it holds the state meanings and
copyable lifecycle templates.

Lead with the result, request, or decision. Use neutral, direct sentences and
name who acts next when action is needed. Report progress only when a
milestone, evidence, risk, or next action changes; avoid repeated status,
filler, invented percentages, or unsupported claims. Include only relevant
fields. Use `pending` for work awaiting completion and `unknown` for facts
not yet verified, with the next verification step. Distinguish local results
from CI results, and implementation readiness from merge completion.

The format does not grant messaging or merge authority. Send required
handoffs directly to the coordinator chat (titled `Cordinator` unless
`AGENTS.project.md` names another) using the chat messaging tool, within user
authorization. Keep the assignment open until its PR is merged and required
follow-up is complete. When available, `skills/agent-coordinator-comms/` in
the template describes the message route for Codex chat tools.

## Coordinator handoffs

Send concise progress and handoff messages in the coordinator chat at these
points:

- Start every agent-to-coordinator message with
  `[Agent <number>] [#<issue> <short task>] [<current state>]`. Start every
  coordinator-to-agent message with
  `[Coordinator] [#<issue> <short task>] [<current state>]`. Use the current
  issue/task and a concise state such as `preflight complete`, `progress`,
  `blocked`, `merge request`, `merged`, or `ready for new task`.
- Put details on the next line, beginning exactly with `Further info:`. Keep
  any following lines as supporting detail for that same message.
- A message in your own task chat, a final answer, a PR comment, or an
  updated chat title is not a coordinator handoff. Use the chat messaging
  tool to send the message directly to the coordinator chat. If direct
  messaging is unavailable, say so plainly and include the intended handoff
  in your final message; never claim the coordinator was notified when no
  message was sent.
- Do not silently stall, contact the user directly about coordination, or
  message other agents directly; route through the coordinator.
- After task preflight, report the issue, scope, default branch and base SHA,
  branch/worktree, ownership/conflict scan, and required checks.
- Report meaningful progress with evidence and the next action.
- Report blockers or ambiguity promptly: what is blocked, evidence,
  files/branches involved, and the decision needed. Stop before making risky
  or conflicting changes and wait for coordinator direction before taking
  dependent action; continue independent work meanwhile.
- When implementation is ready for merge review, use the `merge request`
  state and say “I want to merge PR #<number>” in the `Further info:` line.
  Include its link, tested head SHA, current base SHA, required check and
  review state, and any freshness or conflict blocker. This is a request for
  the coordinator's merge decision; do not merge on your own unless explicitly
  delegated. For example:

  ```text
  [Agent <number>] [#<issue> <short task>] [merge request]
  Further info: I want to merge PR #<number>. Head `<sha>`, base `<sha>`; checks: <results>; review: <state>; mergeability: <state>.
  ```

- If you cannot open or update a PR because GitHub access is unavailable, send
  the coordinator the pushed branch, exact head and base SHAs, local check
  results, and the access blocker. Do not rely on the coordinator finding the
  details in your task chat; the coordinator can open the PR if appropriate.
- After performing an explicitly authorized merge, say “I have merged PR #X”
  and include the resulting default-branch SHA.
- After the task is complete, report completion, final checks, remaining
  limitations, and that you are ready for a new task. Keep the task open
  while its PR or required follow-up is pending.

Coordinator replies use the same two-line structure, with `[Coordinator]` in
the first field. For example:

```text
[Coordinator] [#<issue> <short task>] [progress]
Further info: PR #<number> merged; current default-branch SHA is `<sha>`. Resume the queued work from that base.
```
